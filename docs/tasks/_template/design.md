# 設計: ログイン・新規登録・ユーザー詳細画面

> requirements.md の REQ-001 から REQ-005 に対応する。ここに記載する Gem、DB、ルーティングの変更は後続の実装ループで行い、この時点ではコードを変更しない。

## 対応する要件 ID

- REQ-001: トップページのログイン画面
- REQ-002: 既存アカウントでのログイン
- REQ-003: ログイン失敗時の新規登録への遷移
- REQ-004: 新規登録
- REQ-005: 認証成功後の詳細画面

## API・画面

ブラウザ向けの HTML 画面のみを対象とし、JSON API は対象外とする。

| HTTP | パス | 処理 | 要件 |
| --- | --- | --- | --- |
| `GET` | `/` | ログイン画面を表示する。 | REQ-001 |
| `POST` | `/login` | ログイン ID とパスワードを照合する。成功時は `/profile`、失敗時は `/sign_up` へ遷移する。 | REQ-002, REQ-003 |
| `GET` | `/sign_up` | 新規登録画面を表示する。 | REQ-001, REQ-003, REQ-004 |
| `POST` | `/sign_up` | アカウントを登録し、成功時は `/profile` へ遷移する。 | REQ-004, REQ-005 |
| `GET` | `/profile` | 認証済み利用者のログイン ID のみを表示する。 | REQ-005 |

画面はログイン画面、新規登録画面、詳細画面の 3 つとする。詳細画面ではパスワード、他ユーザーの ID、プロフィール編集操作を表示しない。

## DB・制約

- `users` テーブルを作成する。
- カラムは `login_id` と `password_digest`、および Rails 標準の timestamps とする。
- `login_id` は `null: false` とし、DB のユニークインデックスを付与する。
- `password_digest` は `null: false` とし、平文パスワードを保存しない。
- `User` は `has_secure_password` を用いる。実装時に必要な `bcrypt` Gem を追加する。
- ログイン ID は文字列として扱い、大文字・小文字の区別、文字数、許可文字は未確定事項が決まるまで追加の制約を入れない。

## 処理・状態遷移

```text
未ログイン
  ├─ GET / ───────────────→ ログイン画面
  ├─ POST /login（認証成功）→ 認証済み → 詳細画面
  ├─ POST /login（認証失敗）→ 新規登録画面
  └─ GET /sign_up ────────→ 新規登録画面

新規登録画面
  ├─ POST /sign_up（登録成功）→ 認証済み → 詳細画面
  └─ POST /sign_up（登録失敗）→ 新規登録画面
```

ログインまたは登録成功時には、作成または照合した `User` の ID をセッションに保存する。`/profile` はセッションから現在の利用者を取得し、その利用者だけを表示する。

## 認証・認可

- `User#authenticate` によるパスワード照合を使用する。
- `session[:user_id]` を認証状態として用いる。
- 認証成功時と失敗時のいずれもセッションを再生成または破棄する。失敗後に、前の認証状態を引き継がない。
- `/profile` は認証済み利用者だけが閲覧できる。未認証で直接アクセスした場合はトップページへ遷移させる。
- ユーザー間のデータ閲覧は発生しない。詳細画面は URL パラメータで対象ユーザーを選べない構成にする。
- 本番環境では `force_ssl` を有効にし、HTTP を HTTPS へリダイレクトし、secure cookie と HSTS を有効にする。TLS 終端を信頼するリバースプロキシを導入する場合に限り、そのインフラ設定と合わせて `assume_ssl` の有効化を検討する。現行の Compose 構成では `assume_ssl` を設定しない。
- `POST /login` は IP アドレスごとに 1 分間で 5 回までとする Rails 標準の `rate_limit` を適用する。超過時も通常の認証失敗と同じ新規登録画面への一般的なメッセージを返す。
- 未登録のログイン ID にもダミーの bcrypt digest との照合を行い、登録済み ID のパスワード照合と応答時間の差を抑える。

## エラー処理

- ログイン ID またはパスワードが空、存在しない ID、または不一致パスワードの場合、認証済み状態を作らず新規登録画面へ遷移する。
- ログイン失敗時の表示は「ログインできなかったため新規登録へ進む」旨の一般的なメッセージにし、ID の存在有無を区別して開示しない。
- ログイン試行がレート制限を超えた場合も、ID の存在有無や制限理由を開示せず、通常のログイン失敗と同じ画面・メッセージへ遷移する。
- 新規登録でログイン ID またはパスワードが空、またはログイン ID が重複した場合は、レコードを保存せず新規登録画面を再表示する。入力エラーを利用者に表示する。
- DB のユニーク制約違反が並行登録で発生しても、重複アカウントを作らず登録失敗として扱う。

## Job・外部連携

対象外。メール送信、外部認証、非同期 Job、外部 API 呼び出しは行わない。

## 互換性・移行

- 新規 Rails アプリへの初回 `users` テーブル追加であり、既存ユーザーデータの移行はない。
- MySQL の既存開発・テスト環境で migration とテストを実行する。
- 既存の Rails 8.1.4、Minitest、Docker Compose 構成を維持する。

## 検証計画

- Minitest の統合テストで、トップページのフォーム表示、ログイン成功、ログイン失敗から新規登録画面への遷移、新規登録成功、重複・空入力での登録失敗、未認証の `/profile` アクセスを確認する。
- 詳細画面でログイン ID は表示され、パスワードと別ユーザーの ID は表示されないことを確認する。
- `docs/development/verification.md` に従い、`bin/rails test`、`bin/rubocop`、`bin/bundler-audit`、`bin/importmap audit`、`bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error` を実行する。未実行項目は成功と扱わない。
